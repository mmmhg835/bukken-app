# 設計メモ

## 全体像

```
┌─────────────────────────┐        ┌──────────────────────────┐
│  bukken-app (Public)    │        │  bukken-data (Private)   │
│  GitHub Pages で配信     │──API──▶│  properties.json         │
│  HTML/CSS/JS のみ        │        │  images/<物件ID>/*.jpg    │
└─────────────────────────┘        └──────────────────────────┘
        ▲                                     ▲
        │ ブラウザで開く                        │ Contents API (PUT/GET/DELETE)
   Mac / iPhone ───────────────────────────────┘
```

**なぜ2リポジトリに分けているか**: GitHub Pages を無料で使うには公開リポジトリである必要がある一方、
物件の価格や資金計画は非公開にしたい。アプリのコードにデータを一切置かないことで、
コードは公開したままデータだけを Private に保てる。

## データモデル (`properties.json`)

v1 は「物件」の平坦な配列だったが、同じ建物の別部屋を登録すると築年月・総階数・最寄駅が
重複し、実際に食い違いが発生した。**v2 で建物と部屋に分離**している。

```jsonc
{
  "schemaVersion": 2,
  "updatedAt": "ISO8601",
  "settings": {
    "loan": { "downPayment": 0, "rate": 0.7, "years": 35, "method": "equal", "costRate": 7 },
    "places": [{ "name": "職場", "address": "…", "lat": 35.6, "lng": 139.8 }]
  },
  "buildings": [{
    "id": "b1", "name": "…",
    "address": "…", "lat": 35.64593, "lng": 139.80215,   // 地図用。住所から取得する
    "builtYM": "2005/02", "totalFloors": 45,
    "stations": "…", "walk": "…", "amenities": "…", "memo": "…",
    "cover": "images/b1/…jpg", "coverThumb": "data:…",
    "images": [ /* 外観・共用部 */ ]
  }],
  "rooms": [{
    "id": "p1", "buildingId": "b1",
    "label": "39階",                     // 部屋の呼び名
    "status": "検討中", "rating": 0,     // 自分の検討状態（募集状況とは別軸）
    "listingStatus": "募集終了",          // 募集中 / 商談中 / 募集終了 / 成約
    "listedAt": "2026-05-24",            // 掲載開始日
    "closedAt": "2026-09-09",            // 募集終了日。販売期間の終端
    "priceHistory": [                    // 値下げの経緯。price は常に最新と同期
      { "date": "2026-05-24", "price": 12800, "note": "登録時" },
      { "date": "2026-09-05", "price": 11800, "note": "値下げ" }
    ],
    "price": 16500,                      // 万円
    "area": 113.02, "layout": "3LDK", "floor": 39, "balcony": 17.08,
    "kanrihi": 2.3, "shuzen": 2.1,       // 万円/月
    "loan": null,                        // null なら settings.loan を使う
    "refMonthly": 41.6,                  // 掲載サイトの表示値。自前計算との差を見るため保持
    "reform": "…", "viewNote": "…", "roomNote": "…", "url": "…", "memo": "…",
    "cover": "images/p1/…jpg", "coverThumb": "data:…",
    "images": [{
      "path": "images/p1/xxx.jpg",        // 拡大表示に使う本体
      "thumbPath": "images/p1/xxx_t.jpg", // 格子表示に使う長辺480pxのサムネ
      "category": "間取り", "caption": "", "name": "IMG_7538.JPG",
      "width": 2560, "height": 1920, "bytes": 612345, "addedAt": "ISO8601"
    }]
  }]
}
```

**派生値は保存しない。** 坪単価・管理＋修繕・ローン返済額・年額・築年数は
`util.js` の `derive(room, building, terms)` が都度計算する。条件を変えれば全部屋に即反映される。
販売期間・改定回数・改定総額も同様に `price.js` の `analyze(room)` が都度計算する。

### 建物と部屋のどちらに置くか

| 建物 | 部屋 |
|---|---|
| 名前・住所・座標・築年月・総階数・総戸数・構造・事業者・学区・**共用施設/共用設備/建物構造** | 価格・面積・間取り・所在階・バルコニー・管理費・修繕積立金・リフォーム・眺望・**専有設備**・販売活動 |

迷ったら「別の部屋でも同じ値になるか」で判断する。同じなら建物側。

**専有設備（床暖房・食洗機など）は部屋側**に置いている。リフォーム済みの住戸だけ
設備が違う、という差が実際に出るため。掲載サイトでは建物単位で載っていることが多いが、
それに合わせると部屋ごとの違いが消える。

### 設備はタグで持つ

`js/spec.js` が選択肢を定義し、文字列配列で保存する。自由記述だと表記ゆれ
（「オートロック」「オート ロック」）で比較できなくなるため。

| 保存先 | 中身 |
|---|---|
| `equipmentTags`（建物） | ディスポーザー・24時間ゴミ出し・各階ゴミ置き場・トランクルーム |
| `roomEquipmentTags`（部屋） | 食洗機・床暖房・ビルトインエアコン・SIC・角部屋・ルーフバルコニー |
| `structureTags`（建物） | 免震・制震・二重床 など |
| `facilityTags`（建物） | オートロック・宅配ボックス・ジム・プール など30項目 |

`facilityTags` は項目が多いので `FACILITY_SECTIONS` で
セキュリティ・管理 / 駐車・駐輪 / 共用スペース の小見出しに束ねて表示する。
並びだけで30個から探すのは現実的でないため。

**建物と部屋の切り分けは「どの部屋でも同じか」で決める。** ディスポーザーは建物の設備、
食洗機は住戸ごとに違うので部屋の設備。ここを混ぜると同じ建物の部屋で値が食い違う。

選択肢は意図的に絞っている。数が多いと押すのが面倒になり、結局入力されないため。
`tagPicker()` は**選択肢から外れた値も末尾に残す**ので、リストを絞っても既存データは消えない。

### リノベ区分

`room.renovation` は なし / 一部リノベ / フルリノベ。価格差の理由になるため、
自由記述の `reform` とは別に区分として持つ。v8 への移行時は既存の記述から推定している
（「全室」「全面」を含めばフルリノベ）。

### 比較表

項目を全部並べると縦に長くなりすぎ、違いを探すのに向かない。そこで
**セクション単位の折りたたみ**と**「違いのある項目だけ」**の絞り込みを併用する。
後者は各行の表示文字列を集合にして、要素が1つなら全員同じ値とみなして隠す
（最寄駅や用途地域など、同じエリアを比べていると多くが一致するため）。
定義は `compareSections()` にまとまっており、行の追加はここだけで済む。

### 一覧の2モード

建物ごと（建物カード → 配下の部屋）と部屋ごと（建物をまたいで1列）を切り替えられる。
建物単位は「どの物件か」を見るのに向くが、**安い部屋を横断で探すときは階層が邪魔になる**ため。
状態は `listUI.mode` に持ち、並び替えの選択肢もモードごとに差し替える。

### v1 からの移行

`js/migrate.js` が起動時に自動変換する。同一建物かどうかは
**築年月・総階数・最寄駅・名前の先頭** が一致するかで判定し、
名前から「（29階）」のような部屋を表す括弧書きを取り除いて建物名にしている。

## 相場（売り出し・賃貸・新築）

### 分析タブを相場に統合した

分析タブは**登録済みの部屋20室**を対象にしていた。相場に数万件の実際の売り出しが
入った以上、同じ操作（軸を選ぶ・分布・推移・区分ごとの集計）は**そちらに対してやるほうが
意味がある**ので、相場タブに寄せて分析タブは廃止した。`#/analysis` は相場へ転送する。

| 分析タブにあったもの | 行き先 |
|---|---|
| 傾向分析（散布図・軸の切り替え） | 相場 > 売出 |
| 価格帯の分布 | 相場 > 分布 |
| エリア別・建物別の相場 | 相場 > 建物別（区分は分類で選ぶ。駅・区・住所の3段階） |
| 相場の推移 | 相場 > 推移（月平均 → 年ごとの中央値に変えた） |
| 割安・割高（回帰からの乖離） | 相場 > 概況の「検討中の部屋」（売出中央との差） |
| 設備で絞り込む | **落とした**。売り出しの行に設備は無い。代わりに建物の条件で絞る |

### 絞り込みの軸

混ぜると何で絞ったのか分からなくなるので、全部別の項目にしてある。

| 項目 | 何を選ぶか | どこに効く |
|---|---|---|
| 対象 | 自分の物件（部屋を登録した建物）／すべて | 建物 |
| 検討状態 | 検討中・内見済・本命・申込有・見送り | 建物（その状態の部屋を持つか） |
| 駅 | **最寄駅**（辰巳・東雲・豊洲…）。いくつでも選べる | 建物 |
| エリア | **区**（江東区・川崎市中原区…）。いくつでも選べる | 建物 |
| 住所 | **町名**（東京都江東区東雲…） | 建物 |
| 築年数 | 築5〜40年・40年超 | 建物 |
| 駅徒歩 | 5〜15分・15分超。**選んだ駅までの分**で見る | 建物 |
| 建物 | 建物そのもの（id で選ぶ） | 建物 |
| 事業者 | ブランド・施工・分譲・設計をまとめた一覧 | 建物 |
| 間取り | 3LDK など | 売り出しの行 |
| 広さ | 50㎡未満〜100㎡以上 | 売り出しの行 |
| 売り出し年 | 何年〜何年 | 売り出しの行 |
| 募集状況 | 販売中・終了 | 売り出しの行 |

**駅・エリア（区）・住所は別物。** 「豊洲」で選びたいときと「江東区」で
選びたいときがあり、「東京都江東区東雲」は細かすぎる。それぞれ
`stations` / `wardOf(b)` / `areaOf(b).town` から作る。区で切るのは、町名まで見ると
数が揃わず、市だけだと横浜市が1つになってしまうため（19区に分かれる）。

**駅と区はいくつでも選べる。** 「川崎と横浜の両方」で見たいことが多い。
同じ条件の中は「どれかに当たれば残す」、別の条件どうしは重ねて効く。

**駅徒歩は、選んだ駅までの分で見る。** `walkMinutesOf(b, 選んだ駅)`。
「豊洲まで10分以内」で探しているのに、隣の辰巳まで6分だからという理由で
残ってしまうと条件の意味が変わる。駅を選んでいなければ最短の駅で見る。
選んだ駅が徒歩の記載に無ければ最短に戻す（黙って落とさない）。

**竣工年ではなく築年数。** 何年に建ったかより、いま何年たっているかで探す。

### 選択肢は連動させる

すべて選択制にする（文字入力だと何を打てばいいか分からない）。選択肢は
**その条件だけ外した結果**から作るので、1つ選ぶと他の選択肢も減る。
辰巳を選べば建物の一覧もその32棟だけになる。件数を添えて多い順に並べる。

`targetBuildings(except)` と `saleRows(buildings, except)` の `except` がその仕組み。

**「募集中の建物だけ」という建物の絞り込みは作らない。** 売り出しを読まないと分からず、
読むために絞りたいのに絞れない。募集状況は行の絞り込みで足りる。

### 一度に読むのは60棟まで

条件に合う建物ぶんだけ `store.ensureMarkets()` でまとめて読む。1棟ずつ読むと
読めるたびに描き直しが走るので、全部そろってから1回だけ知らせる。
60棟を超えたら読みに行かず、条件を絞ってもらう。

### 推移は年ごとの中央値で見る

月平均だと件数の少ない月に振られる。年ごとの**中央値**と前年比、それに年平均の伸び
（複利）を出す。**グラフと同じ数字を表にも出す**（字面で追いたいため）。
価格変更のあった行は変更後の価格でも数える（その月に実際その値で出ていたため）。

### 建物は「検討中」と「参考」に分ける

駅ひとつで数百棟入る（武蔵小杉417・豊洲142）。全部を `properties.json` に持つと
1棟2.5KBで **数MB**になり、起動時に読めなくなる。

| | どこに | `store` から |
|---|---|---|
| 検討中の建物（部屋がある） | `properties.json` | `store.buildings` |
| 参考建物（相場だけ見る） | `refs/<n>.json`（300KBごと） | `store.refs` |
| 両方 | | `store.allBuildings` |

一覧・比較・ライフプラン・内見・地図は `store.buildings` だけを見るので、
参考建物が混ざらない（地図の「座標がない建物」に数百棟並ぶこともない）。
相場タブだけが `store.ensureRefs()` を呼んで参考建物を読む。

**部屋を足した建物は検討中へ移る**（`addRoom` が `#promote` を呼ぶ）。
参考側は取り込みでしか書き換えないので、編集の対象になるものは properties.json に置く。

### マンレビの写真は URL だけ持つ

`building.photos` に `https://www.mansion-review.jp/image/mansion/<id>/<画像id>-600.jpg`
を並べる。**画像そのものは取り込まない。** マンレビの「コンテンツの引用・転載について」が
「画像の引用など第三者が著作権その他の権利を有しているコンテンツ」の転載を断っており、
LIFULL HOME'S 提供の写真がこれに当たる。リンクでの参照は制限されていない。

600棟ぶんを取り込めば300MBを超えるという実務上の理由もある。

### ファイルを建物ごとに分ける

```
properties.json          建物・部屋・設定（163KB）
market/b10.json          ブリリアマーレ有明の相場（530KB・1,805行）
market/b15.json          ガレリアグランデの相場（283KB・953行）
...
```

**まとめてはいけない。** アプリは GitHub Contents API で読んでいて、
**1MB を超えると `content` が空で返り、`JSON.parse` で落ちる**。
有明テニスの森駅の10棟だけで約5MB になり、東雲・川崎を足せば確実に超える。

相場タブで**選んだ建物の分だけ読む**（`store.ensureMarket(buildingId)`）。
まだ読んでいない建物は `marketOf()` が `null` を返すので、画面は「読み込み中」を出す。
届いたら `change` が飛んで描き直される。

**未読の建物には書き込ませない**（`#marketFor` が投げる）。読まずに追記すると、
空の配列で上書きして既存の数千行を消してしまう。

保存も建物ごと。`marketDirty` に建物 id が入り、自動保存がその分だけ書き戻す。
相場ファイルは**字下げなしで置く**（機械が書くだけで人は読まない。字下げすると2倍近くなる）。

### エリアごとまとめて取り込む

駅ページから建物 id を拾い、ページ内 `fetch` + `DOMParser` で各棟を読む。
**建物の突き合わせは「総戸数が一致し、かつ名前が前方一致」**。名前だけで寄せると
「プラウド武蔵小杉」と「プラウドタワー武蔵小杉」を取り違える。

**既存の値は上書きしない。** 空の項目だけ埋め、食い違ったら `remarks` に両論併記する。
有明の取り込みでは、構造・管理方式・用途地域・築年月がマンレビと SUUMO で食い違った。



建物ごとに、マンションレビューから写した3種類の価格を貯める。相場タブの4サブタブ
（概況・売出・賃貸・新築）で見る。

| 配列 | 何 | 価格の単位 |
|---|---|---|
| `marketListings` | 中古の売り出し履歴 | 万円 |
| `rentListings` | 賃貸の募集履歴 | **円** |
| `newPrices` | 新築時の分譲価格 | 万円 |

### 賃貸だけ円で持つ

賃料は掲載も生活実感も円で、万円に直すと写し間違える（28.0 と 280,000 を取り違える）。
配列ごとに単位をそろえ、**同じ配列の中では単位を混ぜない**。売買の管理費が万円/月で
賃貸の管理費が円/月なのは、それぞれの価格と単位をそろえた結果。

### 販売中と「記録なし」を分ける

マンレビの販売終了年月には「販売中」と「ー」の2種類があり、どちらも年月が入らない。
終了年月の有無だけで判定すると**2009年の行まで販売中に数えてしまう**ので、
`open` を別に持つ。`open` が無い古いデータは終了年月の有無で見る。

| | `closedYM` | `open` | 販売期間 |
|---|---|---|---|
| 販売中 | null | true | 今月までで数える |
| 終了した | 'YYYY-MM' | false | 差で数える |
| 記録なし（「ー」） | null | false | **出さない**（null） |

### 募集中と募集終了で分ける

部屋には `listingStatus`（募集中 / 募集終了 / 成約）がある。**一覧の既定は「募集中」**で、
ライフプランと比較の対象も募集中だけ。買えない部屋で試算しても意味がないため。

**選択中の部屋だけは例外で、募集終了になっても選択肢に残す**（`planRooms(keepId)`）。
選んでいた物件が急に消えると、何を見ていたのか分からなくなる。

過去に売りに出た部屋は `marketListings` 側にある。**募集終了の部屋を `rooms` に貯めない。**
一覧・比較・ライフプランに他人の部屋が並んでしまう。

### いま出ている数

募集中の件数を**総戸数と並べて出す**。413戸に24件なら5.8%で、売りたい人が多い状態。
2%未満なら少なめ、5%以上なら多めとしている。

**掲載期間は募集中の行だけで見る。** 終わった行を混ぜると「売れるまでの早さ」になり、
「今どれだけ滞留しているか」が見えなくなる。

### 募集中の行から部屋を作る

売出履歴の「販売中」の行は、いま出ている募集情報そのもの。相場タブから
`store.addRoom` に流し込める。掲載サイトのスクショを撮り直さずに済ませるのが目的。

| 売出履歴 | 部屋 |
|---|---|
| `floor` | `label`（「9階」）と `floor` |
| `price` / `area` / `layout` / `balcony` | そのまま |
| `kanrihi` / `shuzen` | そのまま（どちらも万円/月） |
| `listedYM` | `listedAt`（`YYYY-MM-01`） |
| `priceHistory`（`ym`） | `priceHistory`（`date`） |
| `feature` に「角部屋」 | `roomEquipmentTags` |
| `feature` に「リフォーム／リノベーション」 | `renovation` |

**階・面積・価格が同じ部屋が既にあれば作らない**（「登録済み」と出す）。
同じ住戸が何度も売りに出るので、二重登録が起きやすい。

### 概況は直近1年で見る

履歴が17年ぶん貯まると、全期間の中央値は「今の相場」ではなくなる。
ガレリアグランデは全657件の中央が245万/坪、直近1年だけなら587万/坪で、
2倍以上ちがう。**利回り・新築比・検討中の部屋との差はすべて直近1年の中央値で出す**。
全期間の値は添え字として小さく出す（貯めた意味が分かるように）。

直近1年に1件も無い建物では全期間で見る（`recent()` がそう畳む）。

### 概況で何を突き合わせるか

| | 出し方 |
|---|---|
| 表面利回り | 賃料の坪単価 × 12 ÷ 売り出しの坪単価。面積差をならすため坪単価どうしで割る |
| 新築時から何倍 | 売り出しの坪単価 ÷ 新築時の坪単価 |
| 検討中の部屋の位置 | その部屋の坪単価と、売り出し中央との差。賃料中央から想定賃料と利回りも出す |

**賃貸は「募集賃料」であって成約賃料ではない**（マンレビの注記のとおり）。利回りは
上振れしている前提で見る。同じ部屋が同じ賃料で募集され続けると6か月ごとに行が増えるため、
件数は「募集の回数」であって「部屋数」ではない。

### 新築は横軸を階にする

売出・賃貸は横軸が年（時系列）だが、新築分譲価格は**同じ時点で一斉に売られた**ので
年で見ても意味がない。階による価格差を見るために横軸を所在階にしている。

## 相場（売り出し履歴）

`marketListings` は**建物ごとに、過去そこで売りに出た部屋**を貯める配列。
マンションレビューの「販売履歴」を写して足していく。

```jsonc
{
  "id": "m1", "buildingId": "b1",
  "listedYM": "2026-08",        // 販売年月
  "closedYM": null,             // 販売終了年月。null なら販売中
  "floor": 4, "layout": "3LDK", "direction": "東", "feature": "リフォーム",
  "area": 75.67, "balcony": 12.7,
  "price": 9698,                // 万円。価格変更があれば変更後の最終価格
  "priceHistory": [{ "ym": "2026-08", "price": 9998 }, { "ym": "2026-09", "price": 9698 }],
  "kanrihi": 1.184, "shuzen": 1.984,   // 万円/月。部屋と単位をそろえる
  "source": "マンレビ", "note": ""
}
```

### なぜ部屋（rooms）と分けるのか

rooms は**検討している物件そのもの**で、ライフプランや指値の対象になる。
`marketListings` は**他人が売りに出した部屋**で、買う対象ではない。
同じ配列に混ぜると、一覧・比較・ライフプランに他人の部屋が並んでしまう。

### 坪単価は写さない

マンレビの表には坪単価・㎡単価の列があるが、**保存しない**（派生値を持たない原則）。
`price` と `area` から都度出す。マンレビの表示と1円単位で食い違うことがあるが、
こちらの計算が正しい。

### 何が見えるようになるか

| | 出どころ |
|---|---|
| 坪単価の中央・最安・最高 | 全行 |
| 販売期間の中央値 | `listedYM` と `closedYM` の差 |
| 値下げした割合・平均の値下げ幅 | `priceHistory` の初値と最終価格の差 |
| 1年で坪単価がいくら動いたか | 売り出した年を横軸にした回帰の傾き |

散布図には**検討中の部屋も重ねる**。「いま買おうとしている値段は、この建物の過去の
売り出しの中でどのあたりか」が知りたいのが目的だから。価格変更のあった行は
変更後の価格でも点を打つ（実際にその月にその値で出ていたため）。

**販売期間は「0か月」を出さない。** 同じ月に出て終わる行が多く、全部に 0か月 と
付くと読めなくなる。

## 保存の流れ

## 保存の流れ

| 操作 | 実際に起きること |
|---|---|
| フォームを編集 | メモリ上の `store.data` を更新 → `dirty=true` → IndexedDB にキャッシュ |
| 4秒放置 / 「保存」 | `properties.json` を PUT（`sha` 付き）＝ 1コミット |
| 画像を追加 | 端末で本体＋サムネを生成 → **`properties.json` も含めて1コミット**（Git Data API） |
| 画像を削除 | ファイルを DELETE → `properties.json` を PUT |

**衝突制御**: `properties.json` の `sha` を保持し、PUT 時に渡す。別端末が先に更新していると
409/422 が返るので、その場合は最新 sha を取り直してユーザーに再保存を促す（`store.save()`）。

## 販売活動と価格推移

`js/price.js`。値下げの経緯と販売期間が残らないと、指値の判断材料にならないため導入した。

| 指標 | 算出 |
|---|---|
| 当初価格 / 現在価格 | `priceHistory` の最初と最後 |
| 価格改定回数 | 履歴の件数 − 1 |
| 価格改定総額・率 | 現在価格 − 当初価格 |
| 初回改定までの日数・金額 | 1点目と2点目の差 |
| 販売期間 | `listedAt` → 募集終了なら `closedAt`、募集中なら本日 |

**検討状態（`status`）と募集状況（`listingStatus`）は別の軸。** 前者は自分の温度感、
後者は売り出しが続いているかどうか。混ぜると「見送ったが売れ残っている物件」が追えなくなる。

`listingStatus` を募集終了・成約に変えた時点で `closedAt` に当日が入り、販売期間が確定する
（日付は手で直せる）。`price` は常に `priceHistory` の最新と同期するため、表や
ローン計算はこれまでどおり `price` だけを見ればよい。

### グラフ

`js/chart.js` が依存なしの SVG を組み立てる。価格は改定日に階段状に変わるため、
線形補間ではなく**ステップ（横に伸ばしてから縦に落とす）**で描く。
募集中の系列は最終点から右端まで水平に伸ばし、まだ動きうることを示す。
比較タブでは選択した部屋を重ねて描画する。

## 分析

`js/analysis.js` が集計と回帰、`js/analytics-view.js` が画面。
縦軸（表示単位）・横軸（物件属性）・色分けをボタンで差し替えられる構造にしてある。
軸は `METRICS` / `ATTRS` / `GROUPINGS` の3つの辞書で定義しており、
**項目を足すときはこの辞書に1行追加するだけ**で全画面に反映される。

### 画面の操作部品

軸の切り替えは独立したピルではなく、**連結したセグメントコントロール**（`ui.js` の
`segmented()`）で表す。ひとかたまりの中で選択が動くほうが「同じ軸の選択肢」だと伝わる。
選択肢が多い「色分け」だけはドロップダウンにし、ON/OFF は `toggle()` のスイッチにしている。
これらは一覧タブの「建物ごと / 部屋ごと」でも同じ部品を使う。

### 設備での絞り込みと色分け

`hasEquipment()` は建物側・部屋側のどちらのタグも見る。分析するときは
「その部屋で使えるか」だけが問題で、どちらに登録されているかは関係ないため。
色分けには設備ごとの「あり / なし」とリノベ区分も選べる。

### 散布図でどの点がどの部屋かを示す

**色では識別しない。** `SERIES_COLORS` は6色で、建物は15件ある。以前は `i % 6` で
使い回していたため、別々の建物がまったく同じ色になっていた（W Comfort Towers WEST・
グラン・エステ川崎・パークタワー東雲がすべて同じ青だった）。色を足して解決しようとしても、
散布図は任意の2点が隣り合うので、色覚の差を含めて見分けられる色は6色前後が上限になる。

そこで識別の担当を分けている。

| | 担当 |
|---|---|
| 点のクリック | 建物名・部屋・間取り・平米・価格・坪単価・指値を吹き出しで出す。もう一度押すと閉じる |
| 色と凡例 | ざっくりした群分け。6件を超えた分は「その他」にまとめる |
| 凡例にさわる | その系列だけ残して他を薄くする。凡例から点を探せるようにする |

**点の脇に名前を出す案は一度入れて、やめた。** 20点でも18点にしか置けないうえ、
文字が増えて点そのものが読み取りにくくなる。点だけのほうが分布を見る目的に合う。

吹き出しは1つの `<g>` を使い回して動かす。**子に `visibility` を付けてはいけない。**
子の `visible` は親の `hidden` に勝つので、閉じたあとも本文の行だけが画面に残り、
「枠のない文字が散らばる」状態になる（実際に起きた）。行は `textContent` の有無で出し分ける。
影も **CSS の `filter` ではなく矩形をもう1枚敷いて**描く。`<g>` への `filter` は
Chrome でフィルタ領域が更新されず、枠が欠けたり前の描画が残ったりする。

**点の大きさは件数から決める**（`20 / √件数`、3〜5.5 で頭打ち）。物件が増えても
つぶれないようにするため。小さい点は押しにくいので、当たり判定は透明な円を別に重ねて
10px 以上を確保している。

色の割り当ては**絞り込み前の全件の並び**で決める。設備で絞って系列が減ったときに、
残った建物の色が入れ替わらないようにするため。

`SERIES_COLORS` の6色は、色覚シミュレーション（P型・D型）込みで全ペアの距離と
地の色とのコントラストを検証して選んである。**色を足したり差し替えたりするときは、
同じ検証をしてから**。

### 回帰と割安度

`linearFit()` は最小二乗法で直線をあてはめ、相関係数と残差の標準偏差を返す。
散布図では傾向線に加えて ±1σ を薄い帯で描き、そこが「相場の幅」になる。

`residuals()` は各部屋について、横軸の値から期待される価格と実際の差を出す。
**この乖離が買い判断の中心**で、「同じ広さの中でこの部屋は相場より17%安い」が一目で分かる。
2点では必ず直線が引けてしまうため、3件未満では傾向線を出さない。

### 自由記述からの数値の取り出し

駅徒歩は「辰巳7分・東雲12分」のような自由記述なので、`walkMinutesOf()` が
最短の分数を取り出す。竣工年は `builtYearOf()` が「2007/02」を 2007.08 に変換し、
年内の差も傾きに反映させる。住所は `areaOf()` が 都道府県／市区町村／町名 に分解し、
エリア別の相場集計に使う。いずれも保存はせず都度計算する。

## ローン試算

`js/loan.js` が元利均等・元金均等の両方を計算する。掲載サイトの表示値を転記していたが、
サイトごとに前提（頭金・金利）が違い比較にならないため自前計算に切り替えた。
転記値は `room.refMonthly` に残してあり、詳細画面で自前計算と並べて表示する。

条件は `settings.loan`（共通）を使い、`room.loan` が入っている部屋だけ個別条件で計算する。
既定は **1.275% / 50年 / 元利均等**。

### 諸費用

`fees = 価格 × costRate% + costFixed`。既定は7%で、`includeFees` が真なら
**借入額に含める**（借入 = 価格 + 諸費用 − 頭金）。実際に諸費用まで借りる前提で
資金計画を立てることが多いため、既定を「含める」にしている。

`cash` は購入時に現金で用意する額。諸費用を借入に含めないときは頭金＋諸費用になる。

### 掲載サイトの表示値との関係

SUUMO の「元金 27.5万 / 金利 9.7万」は **0.7% / 50年 / 元金均等の初回**だった。
16500 ÷ 27.5 = 600か月（＝50年）、9.7 × 12 ÷ 16500 = 0.705% で逆算できる。
同じ前提で並べ直せるよう、転記値は `room.refMonthly` に残し、比較表にも出している。

### 検証

`tools/verify-loan.mjs` が閉じた式の結果を1か月ずつ回した返済表と突き合わせる。
元利均等は n 回返した残高が 0 になること、元金均等は初回・最終回・総利息が
理論値（利息の総和は等差数列）と一致することを確認する。**計算式を触ったら必ず実行する。**

```bash
node tools/verify-loan.mjs
```

## 家計シミュレーション

`js/lifeplan.js` が計算、`js/lifeplan-view.js` が画面。初期値は
「1.18億円の住宅購入 家計シミュレーション」スライドの内訳をそのまま入れてある
（収入120万／支出119.1万／残り+0.9万）。`tools/verify-lifeplan.mjs` で突き合わせられる。

```
settings.lifeplan = {
  income: [{ id, name, amount }],
  bonus: { annual, include },          // 既定では計画に含めない（上振れバッファ）
  groups: [{ id, name, kind, items: [{ id, name, amount, saving, temporary }] }],
  selectedRoomId,                      // null なら住居費の手入力値を使う
}
```

- `kind: 'housing'` のグループは、部屋を選ぶと**ローン返済＋管理費＋修繕積立金に差し替わる**
- `kind: 'car'` のグループは独立した段として積む。金額が大きく、車の持ち方が
  月次の余裕を左右するため、他の固定費に埋もれさせない
- `enabled: false` の項目は計算から外れる。何を含めた結果なのかを画面で確かめられるようにするため
- `category` は **積立 / 固定 / 変動** の排他3択。
  「収入 → 資産形成 → 住居費 → 固定費 → 変動費」の順に差し引く段階表がこの区分で作られる
- `temporary: true` は期限付きの支出（車ローン・奨学金）。完済後シナリオで除外できる

`waterfall()` が段階表を組み立てる。**住居費と車関連のグループは区分に関わらず独立して積む**ので、
二重計上は起きない（積立＋住居＋車＋固定＋変動＝支出合計になることを `tools/smoke.mjs` で検証）。
最後に残る額が「変動費に使える上限」＝生活費として動かせる金額になる。

### グラフ

`project()` が年単位で収支を伸ばす。期限付きの支出は `remainingYears` で消え、
住宅ローンは返済年数で終わるため、**支出が段階的に下がる様子**が線になる。
`milestones()` が節目（車ローン完済・住宅ローン完済）を返し、縦の破線で示す。

累積資産は「先取りの積立＋月次の残り」の累計。支出が減る年から傾きが変わる。

昇給や物価上昇は織り込んでいない。前提を増やすほど数字の意味が薄れるため、
いまの条件がそのまま続いた場合として見る。

### 指値との比較

`room.offerPrice`（スキーマ v15）。「いくらまで下がったら買えるか」を試算するための
入力値で、派生値ではないので保存する。

**現在価格（`price`）とは別に持ち、ライフプランタブの中だけで価格に代えて使う。**
`price` に上書きすると一覧・比較・分析の「現在価格」の意味が変わり、
相場との比較が成り立たなくなる。`offerRoomOf()` が価格だけ差し替えた
**複製**を返し、元の部屋オブジェクトには触れない。

指値が入っているときは元値でも同じ計算（`calcPlan` と `project`）を回し、差を並べる。
借入額の差が価格の差より大きくなるのは、諸費用（既定7%）も価格に連動するため。

**ローンの数字だけでは判断できない**ので、比較表は 購入・借入 / 毎月の収支 / 長い目で見た差
の3段にし、生活費・変動費に使える上限・毎月の残り・10〜30年後の資産まで載せる。
指値で動かない項目（収入・車・固定費・変動費）も既定で表示する。
何が変わらないかが見えないと、差の大きさを受け取れないため。
「差のある項目だけ」で絞り込める。

グラフでは元値を**破線**で重ねる。色だけで分けると、線が近いところで
どちらがどちらか分からなくなる。

### 画面の数字にも元値を添える

比較表を別に置くだけでは、その下のサマリー・住居費・段階表・支出の内訳が
指値の数字だけになり、何と比べているのか分からなくなる。
そこで `vsBase()` が**差が出ている数字にだけ**「元値 ◯◯　±◯◯」を添え字として並べる。

**元値で置き換えず、添え字にする。** 主役はあくまで指値の側の数字で、
元値は参照先。差が無い項目には出さない（全項目に付くと、動いた項目が埋もれる）。

### 返済負担比率

ライフプランタブの中のサブタブ（`#/plan/burden`）。物件と年収の前提を
ライフプラン側と共有するため、別タブに切り出さずサブタブにしている。

`incomePatterns()` が3通りの年収（本人／本人＋配偶者の半分／本人＋配偶者）について、
**額面と手取りの両方**で返済負担率と年収倍率を返す。額面は審査で使われる数字、
手取りは実際の暮らしでの負担感。負担率はさらにローン返済のみと管理費・修繕込みに分ける。

### 手取りは入力させない

**額面（`grossIncome.*.annual`）だけをこのタブで入力し、手取りは `income` から集計する**
（`netIncomeByWho()`）。以前は手取りもここで別に入力させていたため、ライフプランの収入を
直しても負担率に反映されず、同じ「手取り」が2つの値を持っていた。

集計には収入項目の ON/OFF と、賞与の「計画に含める」がそのまま効く。
誰の収入かは `income[].who`（`primary` / `secondary` / `shared`）で持つ。
**`shared`（その他収入・賞与）はどの見方にも入れる。** 世帯の収入であって
配偶者の分け前ではないため、「本人だけ」で見るときも消えない。

## 画面に説明文を置かない

ラベル・単位・列見出しの副題で意味が伝わるようにし、操作を説明する文章は置かない。
数値の下の小さな添え字は「その数字が何か」を定義するものに限り、
使い方の案内には使わない。空の状態は短い一文で示す。

`affordablePrice()` は、毎月の残りがちょうど0になる購入価格を二分探索で逆算する。
返済額は年数と金利に対して単調なので、閉じた式を解かずに済む。

## 売却の試算

`js/sale.js` が計算、`js/sale-view.js` が画面（`#/plan/sale`）。
買うときの試算だけでは、途中で手放す選択肢を金額で比べられないため足した。

**ライフプランの中のサブタブにしている。** 物件・指値・ローン条件という前提を
そのまま共有できるので、別タブに切り出すと同じ前提を2か所で選ぶことになる。

| 出すもの | 出し方 |
|---|---|
| ローン残高 | `loan.js` の `scheduleAt()`。閉じた式で出す |
| 売却の手取り | 想定売却価格 − 売却諸費用 |
| 手残り | 売却の手取り − ローン残高 |
| 実質負担 | 購入時の現金 ＋ 支払total（ローン＋管理＋修繕） − 手残り |

**売却の諸費用は購入時（`settings.loan.costRate`）と別に持つ**（`settings.sale`）。
買うときは仲介手数料・登記・税、売るときは仲介手数料・印紙・抵当権抹消で中身が違う。
既定は 3.3%（仲介手数料 3%＋6万の税込み相当）＋ 10万円。

想定売却価格は部屋ごと（`room.salePrice`、null なら現在価格）。
`priceMode: 'decline'` にすると年あたりの下落率を織り込む。

`scheduleAt()` は40年分をループで回さず閉じた式で残高を出す。
毎回の再描画で返済表を回すと画面が重くなるため。
`tools/verify-sale.mjs` が1か月ずつ回した返済表と突き合わせて検証する。

**手残りが0以上になる年**（`breakEvenYear()`）が、売り時の判断で最初に見る点になる。

### 指値の表は一覧、比較は比較タブ

`js/lifeplan-view.js` の `offerView()`（`#/plan/offer`）。**全部屋を横に並べて、
その場で指値と相場を入れる**場所。価格・面積・階・築年数・管理費・修繕積立金は
登録済みの部屋から引く。売り出し価格が動いたときに直す場所を2か所にしないため、
手で入れるのは**指値と相場坪単価だけ**。諸費用は「金利と価格」と同じ試算条件
（`planTerms()`）で出す。

並べて比べるのは比較タブに寄せてある。行のチェックは一覧・比較と**同じ選択**
（`views.js` の `togglePick`）に繋いでいるので、選び直しが要らない。

## 内見

`js/viewing-view.js`。サブタブは無く、1つの部屋について**チェックポイントと記録を
1枚に**出す（`#/viewing`）。現地では「見て・付けて・書く」を行き来するので、
分けるとタブを往復するだけだった。古い `#/viewing/check` `#/viewing/note` は
`main.js` の `parseHash()` がこの画面に寄せる。

指値は**ライフプランへ移した**（`#/plan/offer`）。いくらで出すかは「いくらなら
返せるか」の話で、試算金利・諸費用・返済と地続きだったため。`#/viewing/offer` は
`#/plan/offer` に飛ばす。

### チェックポイントは札を押して回す

`spec.js` の `VIEWING_SECTIONS` に38項目を7つの見出しで定義し、部屋ごとに
`viewingChecks`（項目名 → `'ok'` / `'bad'`）で持つ。押していない項目は未確認のまま残る。
1つの札を押すたび **未確認 → ○良い → △気になる** と回るのは、現地で押す回数を
減らすため。3状態の切り替えを別部品にすると、項目数ぶんタップが増える。

自由記述にしないのは設備タグと同じ理由で、あとから部屋どうしを並べられなくなるため。



## 相場

相場坪単価は掲載サイトの外（ISOGE・マンションレビュー）から持ってくる値で、
階や向きの補正が入って住戸ごとに変わるため**建物ではなく部屋**に持つ。

**出どころごとに枠を分ける**（`marketIsoge` / `marketMrev`）。同じ住戸でもサイトに
よって値が違い、1枠にすると「どちらの相場と比べたのか」が残らない。実際に
マンレビ推定は ISOGE より平均6.2%高く出ている。

**持つのは坪単価だけで、グロスは坪数から都度出す。** 画面ではどちらを入力しても
もう一方が出るが、両方を保存すると面積を直したときに片方が古いまま残る。

差は **`相場坪 − こちらの坪単価`** で揃える。＋ほど相場より安く買えるという向き。
売り出しと指値の両方について出すのは、**値引き率が大きいのに相場より高い**という
見え方の理由（売り出し価格そのものが相場から離れている）が読み取れないため。

## 試算金利

`js/lifeplan-view.js` の `planTerms()`。設定の金利に `ui.rateBump`（0.25%刻み）を
足した条件を返し、**ライフプランタブの5サブタブすべて**がこれを使う。

金利が上がったときの影響は返済額だけでなく、返済負担率・売却時のローン残高・
将来の資産にも出る。1か所で切り替えられないと、サブタブごとに前提がずれる。

**設定そのものは書き換えない。** 書き換えると一覧・比較・分析の数字まで動いて
しまうため、上乗せ幅を画面の状態として持つだけにしてある（保存しない）。

### 金利と価格のマトリクス

`matrixView()`。行が価格、列が金利で、マスに住居費と毎月の残りを縦に並べる。

**行は「意味のある価格」だけ**にする。売り出し・指値・ISOGE相場・マンレビ相場の4本で、
刻み幅の等差数列は置かない。根拠の無い数字が並ぶと、相場と見比べながら指値を
決めるのに使えないため。指値の行は額が未入力でも残す（そこが入れる場所になる）。

並びは固定する。価格順にすると**指値を打っている最中に行が動く**。

表の脚に「毎月の残りが0になる価格」を金利の列の真下に置く。指標グリッドに出すと
列数が金利の本数に左右されて空きマスが出るため。

## 地図

`js/map.js`。**API キーが不要**な組み合わせを選んでいる。

- タイル: 国土地理院（`cyberjapandata.gsi.go.jp`）— 帰属表示が必要
- 住所検索: 国土地理院 住所検索API（`msearch.gsi.go.jp`）— 日本の住所に強い
- 描画: Leaflet（cdnjs から地図画面でのみ遅延読み込み）

建物には `lat`/`lng` を保存する。毎回ジオコーディングすると表示が遅く、
外部サービスへの依存も増えるため。距離は球面近似、徒歩分数は 80m/分 で算出。

## デザインの2案

見た目を差し替えたいが、いつでも戻せるようにしたいという要件から、
**スキン方式**で2案を同時に生かしている。

- `app.css` … クラシック（旧デザイン）。すべての土台
- `skin-v2.css` … 新デザイン。**全ルールが `:root[data-skin="v2"]` の下に閉じている**

`js/skin.js` が `data-skin` を切り替え、`localStorage` に保存する。既定は `v2`。
ロジックと DOM は共通なので、**どちらを選んでも機能は完全に同じ**。

新デザインは左サイドバー（狭い画面では下部タブ）、クリーム地に深緑。
`.tab-ico` と `.brand-sub` は新デザイン専用の要素で、`app.css` 側で既定は非表示にしてある。

**新デザインの調整は `skin-v2.css` だけで完結させる。** `app.css` を触ると
クラシック側も変わってしまう。

## 配色

`js/theme.js`。既定は端末設定に従い、明示的なライト／ダーク指定もできる。

- `:root` にライトの値、`:root[data-theme="dark"]` にダークの値
- 端末設定に従う場合は `@media (prefers-color-scheme:dark){ :root:not([data-theme="light"]) }`
- `index.html` の先頭で `localStorage` を読んで即座に属性を当て、リロード時のちらつきを防ぐ

地図タイル（国土地理院）は白地しか無いため、ダーク時のみ CSS フィルタで明度を落としている。

## 画像の上限

アプリ側に枚数制限は無い。実質的な制約は GitHub リポジトリの容量（1GB 以内が推奨）で、
画質設定ごとの目安は次のとおり。設定タブに現在の保存量と残り枚数の概算を表示している。

| 画質 | 1枚あたり | 1GB での目安 |
|---|---|---|
| 標準（1600px） | 約240KB | 約4,000枚 |
| 高画質（2560px） | 約640KB | 約1,500枚 |
| 原寸 | 約3MB | 約330枚 |

`properties.json` は画像1枚につき約200バイトしか増えないため、枚数が増えても保存は重くならない。

## 端末間の設定引き継ぎ（QR ペアリング）

トークンを端末ごとに手入力させるのは現実的でないため、設定済みの端末が QR を表示し、
別端末のカメラで読むだけで引き継げるようにしている。

1. 設定画面で `pairingUrl()` が `#/setup/<base64url(JSON)>` 形式の URL を生成
2. `renderQr()` が QR 画像にする（cdnjs の qrcode-generator を設定画面でのみ遅延読み込み）
3. 読み取った端末は `main.js` の `consumePairing()` で設定を保存し、
   **即座に `history.replaceState` で URL からトークンを消す**

設定はクエリ文字列ではなく**ハッシュ（#）に載せる**。ハッシュは HTTP リクエストに含まれず、
サーバーやアクセスログに残らないため。

> この仕組みは Web 版の制約に対する回避策。ネイティブ化する際は
> キーチェーン＋iCloud に置き換わり、QR ペアリングごと不要になる。

## 画像の扱い

1枚の写真から3つの表現を作る。用途ごとに解像度を分けないと、一覧で拡大ボケが起きるか、
ギャラリーで巨大な画像を何十枚も読むことになるため。

| | 解像度 | 置き場所 | 用途 |
|---|---|---|---|
| 本体 | 画質設定による（既定 長辺2560px） | `images/<ID>/xxx.jpg` | 拡大表示・一覧カードのカバー |
| サムネ | 長辺480px | `images/<ID>/xxx_t.jpg` | ギャラリーの格子 |
| カバー | 長辺320pxの data URL | `properties.json` 内 | 一覧を通信なしで即描画する仮表示 |

画質は `js/image.js` の `QUALITY_PRESETS` で3段階（標準/高画質/原寸）。
**原寸かつ元が JPEG の場合は再エンコードせず元データをそのまま使う**。
間取り図や物件概要など、細かい文字を含む資料が再圧縮で読めなくなるのを避けるため。

### まとめてコミットする理由

複数枚を Contents API で1枚ずつ PUT すると、枚数ぶんコミットが乱立し往復も増える。
`GitHubRepo.commitFiles()` は Git Data API（blob → tree → commit → ref）を使い、
**画像も `properties.json` も1コミットにまとめる**。blob 作成のみ並列4本に絞って
二次レート制限を避けている。

## キャッシュ

- `IndexedDB / kv / data` … 最後に同期した `properties.json`（オフラインでも一覧が開ける）
- `IndexedDB / img / <path>` … 画像 Blob（本体・サムネとも）。表示時に `URL.createObjectURL` して使う
- `sw.js` … アプリのシェル（HTML/CSS/JS）のみ。API 通信とデータには触らない

### 更新が届かない問題への対処

GitHub Pages は静的ファイルに `Cache-Control: max-age=600` を返すため、
素直に `fetch` するとブラウザが最大10分間、古い JS を返し続ける。
実際に「修正したのに画面が変わらない」状態が起きた。

`sw.js` は同一オリジンの取得をすべて `cache: 'no-cache'` で行い、
サーバーに必ず問い合わせる（ETag で変更が無ければ本文は転送されない）。
あわせて起動時と30分ごとに `registration.update()` を呼び、
新しい Service Worker が主導権を取ったら自動で再読み込みする。
`util.js` の `APP_VERSION` と `sw.js` の `VERSION` は**同じ値に揃えて更新する**。

## 意図的に採用していないもの

- **ビルドツール / フレームワーク**: 素の ES モジュールのみ。AI が交互に編集するとき、
  依存やビルド設定の差分で壊れるのを避けるため。
- **バックエンド**: GitHub が唯一の保存先という要件から、サーバーを持たない。
- **git commit による画像管理の最適化**: 枚数が数百を超えたらリポジトリ肥大が問題になる。
  その時点で Git LFS か外部ストレージ（R2 等）への移行を検討する。
